# ピックアップ連携仕様（台本作成システムとの分担）

最終更新: 2026-08-11

台本作成システム（`C:\Users\doras\Music\雑多\台本作成-Shorts` / script_forge）と
このトレンド収集アプリの間で、「どのネタで動画を作るか」の判断を共有するための取り決め。

## 分担

| 段階 | 担当 | 内容 |
|---|---|---|
| 1 | script_forge | 2つのDBを読み、動画IDで重複を除いて一覧表示（読むだけ） |
| 2 | script_forge | ピックアップ操作 → `採用` を true にする |
| 3 | **トレンド収集（本アプリ）** | **ピックアップ済みの一覧表示と、単体・複数・一括の解除** |

**書き込んでよい欄は `採用` と `制作状況` の2つだけ。**
タイトル・URL・再生数・チャンネルといった収集結果には双方とも書き込まない。
行の削除・アーカイブもしない。

### 取り消しは双方から可能（2026-08-11 オーナー判断）

script_forge 側のHTMLからも取り消せる。使うのが一人なので、分担の厳密さより
「押し間違えたその場で戻せる」ことを優先する、という判断。

ただし**HTMLは開いた時点で最新の採用状態を読むこと**。焼き込んだままだと、
`/pickups` で外した結果が反映されず、古い表示のまま操作することになる。
取り消しボタンより、こちらのほうが優先度が高い。

ブラウザから直接 `/api/pickups` を叩く場合は CORS 許可の追加が必要
（現状このアプリは CORS ヘッダーを付けていない）。ローカルのPython経由で
Notionを読み書きする設計なら不要。

## 2つのデータベース

| 通称 | 環境変数 | ID | 中身 |
|---|---|---|---|
| YouTube動画DB | `NOTION_DATABASE_ID` | `3a282a77…` | 競合チャンネルの動画 |
| トレンド企画DB | `NOTION_INTELLIGENCE_DB_ID` | `3ad82a77…` | WEB・SNS・Reddit等から拾った話題 |

IDは `scraper/.env` と `.env.local` の両方、および GitHub Secrets に登録されている。
変更する場合は3箇所すべてを揃える。

### 共通の列（2026-08-11 に動画DB側へ追加して揃えた）

- `採用` … checkbox
- `制作状況` … select（未着手 / 制作中 / 投稿済み / 見送り）

列が無い場合は各コレクターの `ensure_*_db_schema()` が起動時に自動で追加する。
Notion は未定義プロパティを含むページ作成を 400 で弾くため、スキーマ確認は必ず書き込みより先に通すこと。

## API

### `GET /api/pickups`

両DBから `採用 = true` の行を**全ページ**取得し、動画IDで名寄せして返す。

```json
{
  "success": true,
  "count": 2,
  "items": [
    {
      "id": "notionのページID",
      "linkedIds": ["同じ動画が両DBにある場合は複数入る"],
      "origin": "video | topic",
      "originLabel": "YouTube | マルチメディア",
      "title": "...",
      "url": "...",
      "videoId": "...",
      "thumbnail": "...",
      "subtitle": "チャンネル名 または メディアソース",
      "viewCount": 12345,
      "score": 88,
      "status": "未着手",
      "createdTime": "..."
    }
  ]
}
```

`採用` 列がまだ無いDBに対して Notion は 400 を返すが、その場合は空配列として扱うので画面は壊れない。

### `PATCH /api/pickups`

```json
{ "ids": ["ページID", "..."], "adopted": false, "status": "制作中" }
```

- `adopted` … `採用` の値。解除は `false`
- `status` … 省略可。指定すると `制作状況` も同時に更新する
- 単体・複数・一括のすべてがこの1本を通る
- Notion のレート制限（毎秒3リクエスト程度）に合わせ、3件ずつ 350ms 間隔で送る
- **行は消さない。**チェックを外すだけ

### `PATCH /api/intelligence/{id}`

企画DBの1行だけを更新する既存API。`{adopted}` と `{status}` を受け付ける。
`/api/pickups` はこれを両DB対応・複数件対応にしたもの。

## 除外の仕組み（2系統ある）

| 対象 | 場所 | 基準 |
|---|---|---|
| YouTube動画DB | `scraper/config.json` の `youtube.exclude_words` | タイトルの部分一致。英数字語のみ単語境界を見る |
| トレンド企画DB | `intelligence_collector.py` の `is_relevant()` | 鳴潮関連語を含むこと＋他ゲー・コスプレ系を除外 |

`purge_excluded.py` は前者を過去分へ遡って適用する後始末ツール。
`--apply` を付けない限り確認のみで何も消さない。**動画DBにしか効かない。**

## 過去に踏んだ落とし穴

- **重複チェックが直近100行しか見ていなかった**（2026-08-11 修正）
  `page_size: 100` の1回だけで打ち切っていたため、DBが100行を超えた時点でそれ以前が
  「無かったこと」になり、同じ動画が何度も新規追加されていた。
  実測で企画DB 518行のうちユニークな動画は122本しかなかった。**全ページ走査は必須。**

- **品質パトロールが採用済みを巻き込み得た**（2026-08-11 修正）
  Phase 5-B が `採用` を見ずに全行を検査していた。人が判断した行を機械判定で消してはいけない。

- **7日経過カードの自動アーカイブ**
  企画DBには7日で自動アーカイブが走る。`採用 = false` のみが対象なので、
  ピックアップ済みは残る。ただし**採用を外すと7日ルールの対象に戻る**点に注意。

  この仕組みのおかげで、上の重複バグで生まれた既存の重複288行は
  手を触れなくても順次消えた（2026-08-11 時点の実測: 最古の行が5日前で、
  7日より古い行は1行も無かった）。**企画DBの行数を規模感の根拠にしないこと。**
  常に直近1週間分しか入っていない。

- **`/api/intelligence` は直近100件しか返さない**
  横断でピックアップを拾うときは `/api/pickups` を使うこと。

- **Notion のクエリは1万件で頭打ち**
  `has_more: false` を返すため気づきにくい。大量削除時は「対象が無くなるまで繰り返す」形にする。
