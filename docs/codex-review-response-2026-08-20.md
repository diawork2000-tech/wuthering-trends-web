## 1. 回答

綿密なレビューありがとうございます。指摘内容を再確認し、特に確認依頼のあった次の2点について、どちらもCodexの認識が正しいことを確認しました。

### 1-1. 本番の `APP_SECRET` は未設定

本番環境で、認証情報を付けずに次の経路へアクセスできることを実測しました。

- `GET /api/pickups` → HTTP 200
- `GET /` → HTTP 200
- `PATCH /api/pickups` → 更新成功

`src/proxy.js` は `APP_SECRET` 未設定時に `NextResponse.next()` で素通しする、意図的なfail-open設計です。結果として、現在は公開URLを知っていれば画面・APIの双方にアクセスできます。

影響は `/api/pickups` に限りません。

- `/api/pickups`: `採用` と `制作状況` を第三者に変更され得る
- `/api/trigger`: YouTube収集を第三者に起動され得る
- `/api/cron`: YouTube APIクォータとGitHub Actions実行時間を消費され得る
- `/api/intelligence_cron`: Gemini枠・収集処理・Actions実行時間を消費され得る

`/api/pickups` は行の削除やアーカイブを行いませんが、人が決めたピックアップを外せるため、十分に保護対象です。

**結論:** 本番環境をfail-closedへ変更し、認証を最優先で有効化します。ローカル開発の利便性は、本番を開放したままにする理由にはしません。

### 1-2. 制作状況だけの更新で `採用` が変わるのは意図した仕様ではない

現状はAPI側で次の代入を無条件に行っています。

```js
properties['採用'] = { checkbox: body.adopted === true };
```

このため、`{ ids, status }` のように `adopted` を省略すると、意図せず `採用=false` になります。画面側が常に `adopted:true` を同送することで表面化を避けていますが、呼び出し側の作法に依存した壊れた契約です。

さらに、制作状況更新と解除が並行すると、遅れて到着した `adopted:true` が解除を取り消し、Notion上だけ再採用される競合が発生します。

**結論:** `adopted` と `status` は独立した任意フィールドとし、明示的に渡されたプロパティだけを変更します。制作状況変更では `status` だけを送り、採用状態には触れません。

## 2. 総合判断

レビューで見つかった問題は、個別の実装ミスというより、次の4つの構造的な不足に集約できます。

1. **認証境界が任意設定で、未設定時に本番が公開される**
2. **Notion更新が「部分成功する分散処理」であることをAPI/UIが考慮していない**
3. **人の判断を守る保護条件が処理ごとに重複実装され、抜けがある**
4. **自動収集の成功・永続化・デプロイ・監視が一続きの処理として検証されていない**

したがって、目先の行だけを直すのではなく、認証・Notionアクセス・保護規則・自動収集の4点を共通基盤として整理します。

## 4. 修正における確定方針

### 4-1. 認証

本番は `APP_SECRET` 未設定なら起動時またはproxyで503/401を返し、必ず閉じます。

推奨する環境別挙動:

| 環境 | `APP_SECRET` 未設定時 |
|---|---|
| production | fail-closed。画面・APIとも拒否 |
| preview | 原則fail-closed。必要なpreviewだけ専用secretを設定 |
| development | localhostに限り開放可能。開放中であることを起動ログへ明示 |

追加対策:

- cron用認証と人間の画面アクセス用認証を分離する
- cronは `Authorization: Bearer ...` のみ許可し、query stringへsecretを載せない
- PATCH/POSTは `Origin` / `Sec-Fetch-Site` も確認し、CSRFの防御層を追加する
- Cookieへ生の `APP_SECRET` を保存せず、署名済みセッショントークンを保存する
- 認証失敗を構造化ログへ残す。ただしsecret本体は絶対に記録しない
- Vercelの環境変数設定後、認証なしGET/PATCHとcron経路が401になることを本番で確認する

### 4-2. `/api/pickups` の契約

更新は「渡されたフィールドだけを変更する」PATCH本来の意味に揃えます。

```json
{
  "ids": ["notion-page-id"],
  "adopted": false
}
```

```json
{
  "ids": ["notion-page-id"],
  "status": "制作中"
}
```

検証規則:

- `ids`: 必須、配列、UUID形式、重複排除、上限あり
- `adopted`: 省略可能、指定時のみboolean
- `status`: 省略可能、指定時のみ `未着手 / 制作中 / 投稿済み / 見送り`
- `adopted` と `status` が両方未指定なら400
- 対象IDが動画DBまたは企画DBに所属することを確認
- 同じIDを重複更新しない
- 1回の更新件数に安全な上限を設定する

APIレスポンスは「全体の成否」だけでなくID単位にします。

```json
{
  "success": false,
  "requested": 4,
  "updated": ["id-1", "id-2", "id-3"],
  "failed": [
    { "id": "id-4", "status": 429, "code": "rate_limited", "retryable": true }
  ]
}
```

UI側は部分失敗時に全体を巻き戻さず、次の順で収束させます。

1. 成功IDは確定
2. 失敗IDだけ画面に残す
3. エラー内容と再試行ボタンを表示
4. 最後にGETでNotionの実状態へ再同期

### 4-3. Notionアクセス共通化

現在は複数ファイルが個別に `fetch` / `requests` を行い、レート制御・再試行・エラー表現がばらばらです。JavaScript側とPython側で、それぞれ共通Notionクライアントを作ります。

共通機能:

- 1リクエストずつ送信し、原則350ms以上の間隔を確保
- 429は `Retry-After` を尊重
- 502/503/504は上限付き指数バックオフ＋jitter
- 401/403/validation errorは即時失敗
- ページング途中失敗はpartial dataとして成功扱いしない
- request ID、対象処理、試行回数、結果コードを構造化ログへ記録
- secret・本文全文・個人情報はログへ出さない
- タイムアウトと最大総実行時間を設定

Vercelの複数インスタンス間で完全なグローバルレート制御はできないため、当面は次も併用します。

- item単位pendingで同一画面からの並行更新を抑止
- 一括操作中は更新系UIを一時的に無効化
- APIごとの件数上限
- 大量操作は小分けし、失敗分のみ再試行
- 将来、同時利用が増えた場合だけ外部キューを検討

### 4-4. 人の判断を守る共通規則

自動アーカイブ、品質パトロール、除外語purgeのすべてで同じ関数・同じテストデータを使います。

自動処理してよい条件:

```text
採用 = false
かつ 制作状況が未設定または未着手
かつ 処理固有の条件に一致
```

自動処理してはいけない条件:

- `採用=true`
- `制作状況=制作中`
- `制作状況=投稿済み`
- `制作状況=見送り`

安全策:

- 実行前に対象件数・保護件数・理由別件数を出す
- 異常に多い場合は自動停止する上限を設ける
- dry-run結果をログまたはartifactに保存する
- アーカイブしたpage IDと理由を監査ログへ保存する
- 実行後に対象件数と成功件数が一致しなければ警告する
- 将来の完全削除は実装せず、Notionのアーカイブだけを使う

### 4-5. 重複防止

重複防止は書き込み可否を決める安全装置なので、途中失敗時に続行してはいけません。

```text
全ページ走査成功 → 新規候補を書き込み可能
全ページ走査失敗 → 収集結果はローカル保存のみ、Notion書き込み中止
```

追加改善:

- URLを正規化してから比較する
- YouTube URLは検証済みvideo IDを正規キーにする
- URLのtracking queryを必要に応じて除去する
- titleだけの一致は強すぎるため、URL優先・titleは補助判定にする
- 1run内のdedupeとNotion既存dedupeで同じ正規化関数を使う
- 走査成功時刻と登録件数をログに残す

### 4-6. 競合日程

#### 永続化

- `.github/workflows/run_intelligence.yml` のstage対象へ `src/data/rival_schedule.json` を追加
- `scripts/vercel-ignore.sh` の自動生成一覧にも追加
- commit/push失敗を `|| true` で握り潰さない
- push競合時は回数制限付きでpull/rebase/retryし、最終失敗を明示する

#### マージ

- versionがある場合は正規化versionを主キーにする
- versionがない場合は `game_id + source + title/label` 等の安定情報を使う
- 日付変更は「新しい別イベント」ではなく、同一イベントの更新として扱える近接日照合を入れる
- 辞書丸ごと置換をやめ、非null・根拠の強いフィールドを優先する
- 手入力・公式確定・自動抽出・周期予測の由来を記録する
- 公式確定値を、未確定値やnullで上書きしない

推奨する由来情報:

```json
{
  "version": "7.1",
  "date": "2026-09-23",
  "confirmed": true,
  "source_type": "official_or_guide",
  "source_url": "...",
  "observed_at": "2026-08-20T00:00:00Z"
}
```

#### 鮮度

全体の `updated_at` だけでなく、ゲームまたはソース単位で次を持ちます。

- `last_attempt_at`
- `last_success_at`
- `last_http_status`
- `last_item_count`
- `consecutive_failures`

これにより、4タイトル成功・1タイトル失敗の場合、失敗した1タイトルだけを次回優先して再試行できます。

#### 日付・保持

- `datetime.strptime(..., "%Y-%m-%d")` 等で実在日を検証
- 過去60日より古くても、ゲームごとの最新の過去1件は保持
- 予測を伸ばす起点となる確定日を必ず残す
- ファイルは一時ファイルへ書き、検証成功後にatomic replace
- 更新前ファイルを短期バックアップとして保持

### 4-7. Geminiフォールバック

エラー理由ごとに挙動を分けます。

| エラー | 挙動 |
|---|---|
| 503 / service unavailable | 同モデルを指数バックオフで最大2〜3回 |
| 429 / per-minute rate limit | `Retry-After` が短い場合だけ1回再試行 |
| 429 / daily quota exceeded | そのrunは中止。別モデル連打をしない |
| 404 / model not found | 次の明示的な安定モデルへ切替 |
| JSON不正 | 1回だけ修復プロンプト、または既存データ維持 |
| 401/403 | 設定異常として即時停止・警告 |

品質優先の候補順:

1. `gemini-3.6-flash`
2. `gemini-3.5-flash`
3. `gemini-3.5-flash-lite`

モデル名は設定へ移し、コードへ散在させません。モデルごとの成功率・JSON妥当率・平均処理時間をログへ残し、実測で順序を見直せるようにします。

### 4-8. カレンダー

終了日なしイベントは、イベント開始日から41日ではなく、所属するバージョンの終端まで表示します。

```text
所属バージョン = event.start_date以前で最も近いversion開始日
終端 = 次version開始日の前日
次version不明 = 所属version開始日 + 41日
```

この処理なら、バージョン開始から30日後に始まったイベントがさらに41日伸びることはありません。

追加修正:

- ISO日付を端末timezoneへ変換せず、暦日として扱う
- DSTやJST以外の端末でも同じ列に表示する
- `role="dialog"`、`aria-modal`、Escape、focus trap、復帰フォーカスを実装
- 記号だけのボタンへaccessible nameを付ける
- 競合ゲーム切替へ `aria-pressed` を付ける
- `title` 属性だけに重要情報を置かない

### 4-9. 除外フィルタ

日本語の部分一致は維持しつつ、半角英数字だけASCII境界として扱います。

```python
pattern = rf"(?<![A-Za-z0-9_]){re.escape(word)}(?![A-Za-z0-9_])"
```

最低限の回帰ケース:

| 入力 | 期待 |
|---|---|
| `プレイヤースキル次第で最強火力` | 除外しない |
| `鳴潮MMD` | 除外する |
| `MMD鳴潮` | 除外する |
| `cosplay鳴潮` | 除外する |
| `鳴潮fanart` | 除外する |
| `Ver.3.5 ストーリーイラスト壁紙` | 除外しない |
| `ゲーム内新衣装まとめ` | 除外しない |
| `徳島の阿波踊り 鳴潮連` | 除外する |
| `逆境深塔 攻略` | オーナー方針どおり除外する |
| `マトリクス 攻略` | オーナー方針どおり除外する |
| `クライシス 攻略` | オーナー方針どおり除外する |

`落書き`、`らくがき`、`切り抜き` は形態上の包含事故は確認されていません。ただし正当なPV抜粋や否定文を落とす意味上の誤判定はあり得るため、今後は除外理由と件数を記録し、実測で判断します。

## 6. 受け入れ基準

### 認証

- productionで `APP_SECRET` 等の必須認証情報が未設定なら、画面とAPIが開かない
- 認証なしのGET/PATCH/cronが401または明示的な拒否になる
- 正しい画面セッションと正しいcronトークンだけが通る
- URL、ログ、エラー本文にsecretが残らない

### pickups

- `{ ids, status }` は採用状態を変更しない
- `{ ids, adopted }` は制作状況を変更しない
- status変更中に解除しても、解除が後から復活しない
- 片方DBだけ失敗した場合、成功・失敗IDが識別できる
- 部分失敗後、UIが再GETでNotion実態と一致する
- 429時に `Retry-After` を尊重し、上限超過後は明示失敗する
- 同一IDは1回だけPATCHされる
- 不正status、空更新、過大件数、許可外page IDは拒否される

### データ保護

- 採用、制作中、投稿済み、見送りの行はpurge/cleanup/patrolでアーカイブされない
- 対象件数が安全上限を超えた場合、自動停止する
- アーカイブ結果をpage IDと理由から追跡できる

### dedupe

- 2ページ目以降のNotion取得に失敗したrunでは新規書き込みが行われない
- 次回成功時に正常復帰する
- URL表記違いの同一YouTube動画が重複登録されない

### 競合日程

- Actions実行後、変更された `rival_schedule.json` がmainへ保存される
- データファイルだけの更新では不要なVercel buildを消費しない
- 1ソース失敗時、成功タイトルは更新し、失敗タイトルは次回優先再試行できる
- 同一versionの既知のnote/new character情報をnullで消さない
- versionなしの日付変更で新旧2件に増えない
- 不正日付でファイルを壊さない
- 各ゲームの最新過去1件が必ず残る

### カレンダー

- 終了日なしイベントが所属バージョン終端を超えない
- JST以外の端末でも日付がずれない
- キーボードだけで開閉・月移動・フィルタ操作ができる

## 7. テスト計画

### 7-1. API単体テスト

- adoptedのみ、statusのみ、両方、どちらもなし
- 空IDs、重複IDs、不正UUID、上限超過
- 不正status
- 許可外DBのpage ID
- Notion 200 / 400 / 401 / 403 / 429 / 500 / network error
- linkedIdsの一部成功・一部失敗
- 先行status更新／後続解除、先行解除／後続status更新
- GETの片方DB失敗、両方失敗、ページング途中失敗
- 任意ドメインの `?v=`、偽 `youtu.be.example`、不正video ID

### 7-2. Python単体テスト

- 除外語の正例・負例を固定データ化
- 保護状態4種が全自動アーカイブ処理から除外される
- dedupeの1〜Nページ成功と途中失敗
- rival mergeのversionあり／なし／日付変更／null field
- 不正日付、閏年、月末
- 60日超過時の最新過去1件保持
- Gemini 429 quota、429 rate limit、503、404、JSON不正

### 7-3. 失敗注入テスト

本番Notionを使わず、モックで次を再現します。

- 4件中3件成功・1件429
- 1ページ目成功・2ページ目timeout
- Retry-After後に成功
- 503が2回続いて3回目に成功
- status更新のレスポンス順逆転
- workflowのgit push競合

### 7-4. E2E

- 認証あり／なし
- 単体解除、複数解除、全件解除
- status変更、連続変更、変更直後の解除
- 読み込み失敗時に空一覧を表示しない
- カレンダーの日付、週跨ぎ、他タイトル切替
- モバイル自動再生とiframe数

### 7-5. CI

推奨順:

1. JSON構文検証
2. ESLint
3. JS単体テスト
4. Python compile / pytest
5. Next.js build
6. 生成ファイルschema検証

現在repo全体のlintは、Gitで無視されているルート `/test.js` の不正エンコーディングで失敗します。先にESLintのignore対象を明示するか、所有者確認後に不要ファイルを整理し、CIでlintを常時通せる状態にします。

## 8. これ以上の業務効率化案

以下は今回の不具合修正に加えて、同種の確認・復旧・手作業を減らすための提案です。

### 8-1. 「安全な自動化」の共通実行フレーム

purge、cleanup、quality patrol、スケジュール更新を、次の共通段階で実行します。

```text
取得 → 検証 → 差分計画 → 安全上限確認 → 適用 → 再取得検証 → 監査記録
```

各処理が独自に直接PATCHする状態をやめることで、dry-run、件数上限、保護条件、再試行、監査を一度実装すれば全処理で使えます。

### 8-2. 操作監査ログ

人・Web UI・cron・自動cleanupのどれが状態を変えたかを追跡できるようにします。

最低限記録するもの:

- 実行ID
- 実行種別
- 開始・終了時刻
- 対象page ID
- 変更したプロパティ名
- 変更前後の値
- 成功・失敗・試行回数
- エラーコード

「15分間届かなかった」「誰かの採用が消えた」を、証言ではなくログから特定できるようになります。

### 8-3. 緊急停止スイッチ

本番障害時にデプロイを待たず、破壊的な自動処理だけ止められる設定を用意します。

- `READ_ONLY_MODE`: 更新APIを503で停止し、GETだけ許可
- `DISABLE_AUTO_ARCHIVE`: cleanup/purge/patrolを停止
- `DISABLE_EXTERNAL_TRIGGERS`: cron/triggerを停止
- `DISABLE_GEMINI`: Gemini呼び出しを停止し既存データ維持

画面上部に現在の制限状態を表示し、止まっている理由が分かるようにします。

### 8-4. 収集ソース健全性ダッシュボード

各ソースについて次を一覧表示します。

- 最終取得成功
- HTTP status
- 取得件数
- 前回との差
- 連続失敗回数
- 0件継続日数
- enabled/disabled

TogetterやTikTokのような「動いているように見えて0件」を、数か月後ではなく当日発見できます。

通知条件例:

- 2回連続HTTPエラー
- 3回連続0件
- 通常件数から90%以上減少
- 全ソース失敗
- Gemini解析成功率が一定以下

### 8-5. 手動確認を例外だけに絞る

毎回全件を見るのではなく、システムが次だけを「要確認」として出します。

- 自動マージで競合した日程
- confirmed値が変化したもの
- 日付が大きく動いたもの
- 新キャラ有無がtrue/falseで食い違うもの
- purge候補だが採用履歴があるもの
- 除外語へ初めて一致した表現

人間は通常ケースではなく、判断が必要な例外だけを確認します。

### 8-6. 変更前後のプレビュー

管理操作は適用前に次を表示します。

```text
対象: 24件
変更: 採用 true → false
保護により除外: 3件
推定所要時間: 9秒
```

大量処理では対象一覧をJSON/CSVとして保存できるようにし、適用後の照合にも使います。

### 8-7. 冪等性キー

解除やcron起動に実行IDを付け、同じ要求の二重送信を安全に無視できるようにします。ブラウザの再送、通信再試行、二重クリック、repository dispatchの重複があっても同じ処理を2回行いません。

### 8-8. GitHub Actionsの同時実行制御

workflowへ `concurrency` を設定し、同じ収集処理が重複起動しないようにします。

候補:

- trend collectorは同時に1つだけ
- intelligence collectorは同時に1つだけ
- 新しい手動実行で古い実行をcancelするかは、データ書き込み段階を考慮して決める
- commit/push部分は競合に強い共通scriptへ集約

これにより、Notionレート超過、重複登録、git push競合、Gemini枠の二重消費を減らせます。

### 8-9. 設定と契約の一元化

次を定数またはschemaとして一元管理します。

- 制作状況の選択肢
- 保護対象status
- Notionプロパティ名
- 許可DB ID
- Geminiモデル候補
- 日程データschema version
- API request/response schema

JS・Python・Notionスキーマで同じ文字列を個別管理しないことで、「一方だけ選択肢が増えた」事故を防ぎます。

### 8-10. 生成データのschema version

`rival_schedule.json` 等に `schema_version` を持たせ、API側が対応外の形式を読み込んだ場合は黙って誤表示せず、既知のバックアップへフォールバックします。

### 8-11. 自動バックアップと復旧手順

「データは絶対に消さない」という方針に合わせ、次を自動化します。

- 変更前の対象値を監査ログへ保存
- 日次でNotionの重要プロパティをJSON export
- Git管理データはatomic write＋直前バックアップ
- 復旧scriptはpage ID単位で元の値へ戻す
- dry-runで復旧対象を確認してから適用

### 8-12. 状態機械としての制作フロー

`採用` checkboxと`制作状況`を完全に独立させるだけでなく、将来的には許可された遷移を明示します。

```text
未着手 → 制作中 → 投稿済み
未着手 → 見送り
制作中 → 見送り
```

ただし、現時点で厳格な遷移制限を入れると運用を妨げる可能性があります。まず監査ログだけ取り、実際に発生している遷移を確認してから制限します。

### 8-13. 投稿実績の自動還流

既存の `GAS-Youtube用` / `youtube_automator` を調査し、投稿済みカードに次を自動追記します。

- 投稿動画URL
- 公開時刻
- 24時間再生数
- 7日再生数
- 視聴維持率等、取得可能な指標

これにより、ピックアップの判断と実際の成果を結び、除外・スコア・おすすめ3本を実績ベースで改善できます。

### 8-14. 「今日やること」への集約

運用画面をデータ一覧ではなく、次の優先タスクへ変換します。

1. 今日作る候補3本
2. 制作中で止まっているもの
3. 実装日が近いのに未着手のもの
4. 要確認の日程競合
5. 収集ソース異常

人間が複数画面を巡回して異常や次の作業を探す時間を減らします。

### 8-15. SLOと週次サマリー

システムの正常性を感覚ではなく指標にします。

例:

- 収集成功率 99%以上
- Notion更新成功率 99.5%以上
- 部分失敗の未解決件数 0
- ソース無警告期間
- Gemini JSON妥当率
- 重複登録率
- 採用から制作開始までの時間
- 制作中から投稿までの時間

週次でDiscordまたはHTMLレポートへまとめ、異常の早期発見と業務改善に使います。

## 10. Codexへの依頼

上記方針で問題ありません。修正に入る場合は、まず **Phase 0とPhase 1** を1つの安全性改善単位として進めてください。

実装時の制約:

- 本番Notionを自動テストに使わない
- 既存の採用・制作状況・アーカイブ状態を検証目的で変更しない
- 変更前に対象ファイルと関連するNext.js 16同梱ドキュメントを確認する
- 本番認証の有効化は、コード修正と環境変数設定の両方が揃ってから検証する
- データ移行が必要ならdry-runとバックアップを先に用意する
- 修正は小さな論理単位で行い、各段階でlint/test/buildを通す
- 自動生成ファイルやログを不要にコミットしない
- 既存の未追跡 `.agents/`、`.claude/`、`skills-lock.json` には触れない

Phase 0/1完了後に、変更内容・テスト結果・残課題を報告し、Phase 2以降へ進む前に一度確認を取ってください。
